- 최종 목표는 Android·iOS 스토어에 출시하는 앱이다. 스토어 출시 조건이 까다로워서, 베타 테스트가 끝날 때까지는 **Flutter Web으로 배포해 브라우저에서 테스트**한다.

- 단계: ① Flutter Web 개발·내부 테스트 → ② 웹 베타 테스트 → ③ Android·iOS 빌드와 실기기 검증 → ④ 스토어 출시. ②의 배포 위치는 GitHub Pages(`https://magician-park.github.io/FarmCargo/`)로 정했다. GitHub Pages는 정적 파일만 제공하므로 서버·DB가 필요한 기능을 실제로 쓰는 베타 테스트는 별도 서버를 정한 뒤에 가능하다. ②의 대상·기간과 ③·④의 일정은 아직 정하지 않았다.
- 웹에서 통과한 것이 앱에서도 동작한다고 보장하지 않는다. 카메라·사진·위치·푸시·권한·파일 저장·보안 저장소 같은 기능은 앱 단계에서 다시 검증한다.
- 아래의 ‘앱’은 제품 요구사항을 지칭한다. 실제 서버·DB가 없는 동작은 합성 데이터·시연으로 구분한다.
- 공통 규칙의 기준은 저장소 루트 [AGENTS.md](../../AGENTS.md)다.

## 1. 서비스 정의와 범위

팜카고는 화주가 올린 운송 일거리를 사업자·지역 인증 절차를 거친 차주가 선택하여 운행하도록 연결하는 운송 알선 앱이다.

- 화주 가치: 운송에 신경을 덜 쓰게 해서, 공장주와의 커뮤니케이션에 더 집중할 수 있도록 업무 부담을 덜어준다.
- 차주 가치: 안정적인 일감과, 동선 최소화·최적화로 운송 부가 비용(톨비·기름값 등)을 줄이고 이득을 키우는 것을 목표로 한다. 차주가 원하는 동선의 일감을 고를 수 있게 한다. 자동 경로 최적화의 구현 방식과 절감액은 아직 정하지 않았다.
- 초기 기능: **화주·차주 입력 → DB 저장 → 화주 간 일감 비공개 → 게시글 형식 일감 목록 → 차주 선택·운행**.
- 화주 홈은 배차 작성과 나의 배차로 연결되며, 본인 일감을 확인·수정하는 방향이다.
- 차주 앱은 홈과 일감 목록 탭으로 나눈다. 홈에는 추천 맞춤 오더를 두고, **일감 목록은 별도 탭에서 게시글 형식으로 쭉 나열**한다(사용자 결정 2026-11-04). 추천 기준(별점 혜택·동선 반영 여부)은 아직 정하지 않았다.
- 운영·인증·증빙·제재·혜택은 확인된 요구로 관리하되 세부 방식과 구현 순서는 구체화해야 한다. 운영에는 변수·문제 발생 시 고객센터(전화·카카오톡)가 해당 화주·차주에게 전화로 전후 사실을 확인하고 민원을 처리하는 방식이 포함된다.
- 서비스 AI(OCR 포함)·자주 쓰는 품목 선택지는 기본 틀 구현 뒤 검토한다. 개발 도구로서의 AI 사용과 구분한다. 가입 서류의 사진 기반 자동 입력은 초안에 있으나 도입 시기는 미정이다(D08).
- 장기 공장·창고 확장: **공장의 원료 발주 → 화주 원료 접수·창고 발주 명령 → 운영 측 조달 → 운송 연결**. 실제 앱 기능·조달 책임·시기는 추후 결정한다.

## 3. 가입·로그인 초안(D15·D16)

옵시디언 `14 회원가입과 인증`의 ‘10/31 작성한 회원가입 절차 초안’을 구현 기준으로 옮겼다. 더 운반 영상에서 관찰한 절차와 구분한다. 구현 상태는 Flutter 데모(샘플 데이터·시연) 기준이다.

| 단계 | 초안 | Flutter 데모 구현 상태 |
|---|---|---|
| 최초 진입 | 이용 권한 허용 → 로그인·회원가입 로비 | 구현. 카메라·사진·위치·알림·전화 5종을 안내(사용자 결정 2026-11-04). 사유 문구는 임시이며 실제 권한 요청은 하지 않음 |
| 로그인 | 휴대폰 번호(아이디)·비밀번호, 뒤로 가기, ‘비밀번호를 잊으셨나요?’, ‘혹시 회원이 아니신가요?’. **이메일은 쓰지 않음**(사용자 결정 2026-11-04; 옵시디언 초안은 이메일 로그인) | 구현(샘플 데이터 대조). 숫자 11자리만 입력됨 |
| 비밀번호 복구 | 초안은 가입 이메일의 재설정 링크였으나 이메일을 쓰지 않으므로 **휴대폰 문자 인증 → 새 비밀번호·확인 → 성공 팝업**으로 바꿈(사용자 결정 2026-11-04 확정). 이미 변경한 뒤 다시 설정하면 ‘인증시간이 만료되었습니다’ 팝업 | 구현. 문자는 보내지 않고 데모 번호를 안내. 인증 후 받는 재설정 토큰은 3분·1회용(유효 시간 3분은 사용자 결정 2026-11-04). 가입되지 않은 번호도 같은 화면으로 진행되고 인증에서 막힘 |
| 가입 공통 | 이름·비밀번호·확인(일치 확인, 모든 칸 정상 전 다음 비활성), 문자 인증(필수, 번호는 아이디라 중복 불가), 약관 | 구현. 이메일 입력은 없음. 이미 가입된 번호면 휴대폰 인증 단계로 돌아감. 문자는 보내지 않고 데모 번호를 안내. 약관 항목은 타사 참조 사진 기반 임시 초안이며 약관 전문 없음 |
| 차주 | 화물운송종사자격증(성명·생년월일·자격증번호·자격취득일) → 사업자등록증. 사진 촬영 후 자동 입력·직접 수정 | 구현. 자동 입력은 고정 샘플 값 |
| 화주 | 주민등록증(실물 또는 모바일 신분증) → 사업자등록증 **사진만 수집**(입력·자동 입력 없음, 사용자 결정 2026-11-04) | 구현. 신분증은 실물 촬영만 되고 모바일 신분증은 준비 중 안내 |
| 완료 | 가입 완료 창·로그인하기 → 로비 → 재로그인 후 제품 로비 | 구현 |
| 비밀번호 저장·검증 | 프로토타입은 **Firebase Auth**, 앱 출시 때 **Argon2id**(사용자 결정 2026-11-04 확정) | 미연결. 데모는 `MockAuthRepository`의 샘플 데이터로 대조하며 `app/pubspec.yaml`에 Firebase 패키지가 없음 |

- 차주 사업자등록증 항목: 등록번호·상호명·성명·생년월일·개업 연월일·사업장 소재지·사업의 종류·발급사유·공동사업자·사업자 단위 과세 적용 여부(여/부)·전자세금계산서 전용 이메일·발급일자·관할 세무서. 발급사유와 공동사업자는 해당 없을 수 있어 선택 입력이며 나머지는 필수로 가정했다.
- 화주는 사업자등록증 사진만 수집하며 입력을 시키지 않는다. 사진 확인은 사측이 하는 방향이고, 화주에게 필요한 항목(세무서·전자세금계산서 수신 주소 등)은 정산 정책(D09)이 정해질 때 다시 정한다.
- 차주 사업자등록증의 ‘전자세금계산서 전용 전자우편주소’는 계정 이메일이 아니라 서류에 적힌 항목이므로 **유지**한다(사용자 결정 2026-11-04).
- 미구현·미정: 차량번호·차종·톤수와 지역 인증이 가입의 어느 단계인지, 사측의 서류·사진 대조 확인과 최종 완료 화면의 순서, 심사 중 접근 범위, 승인·보완·반려·재제출·결과 알림, 원본 보관·열람, 가입 OCR의 초기 도입 여부와 수동 입력 대안, Firebase Auth 연결(프로젝트·설정)과 휴대폰 번호+비밀번호 로그인 구성, Argon2id로 옮기는 방법.
- Firebase Auth의 기본 로그인 방식(이메일·비밀번호, 휴대폰 문자 인증)과 ‘휴대폰 번호 아이디 + 비밀번호’ 요구를 어떻게 맞출지, Firebase Auth에서 Argon2id로 옮길 때 기존 비밀번호를 어떻게 넘길지는 설계 전에 공식 문서로 확인한다.
- 자동 입력(OCR)과 사측 대조 확인은 다른 단계다. 자동 입력만으로 인증이 완료됐다고 처리하지 않는다.

- 계근표·하차 서명 인증을 회원가입 제출 서류로 합치지 않는다.
