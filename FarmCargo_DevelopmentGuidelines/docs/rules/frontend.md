# 프론트엔드·화면 개발 규칙

작성일: 2026-11-03
읽기 순서: [저장소 AGENTS.md](../../../AGENTS.md) → [현재 요구사항](../requirements.md) → 이 문서
프레임워크는 Flutter이며 상태 관리는 Riverpod, 라우팅은 go_router다(실제 `app/pubspec.yaml` 기준). 새 방식은 사전 합의 없이 도입하지 않는다.

## 현재 개발 적용 기준 — Flutter(웹 베타 → 앱 출시)

- 제품 화면은 `app/lib/`의 Flutter 코드로 만든다. 같은 코드로 웹 베타를 배포하고, 베타 종료 후 Android·iOS 앱으로 빌드한다.
- `app-demo.html`에는 권한 안내·로비·로그인·회원가입·비밀번호 재설정 흐름이 Flutter와 같은 규칙(입력 검증, 인증번호 3분, 재설정 3분)으로 들어 있다. 이 흐름을 Flutter에서 바꾸면 `app-demo.html`도 함께 고친다. 옛 역할 선택·가입 화면은 이 흐름으로 대체하면서 삭제했다.
- `app-demo.html`·`farm-cargo-mockups.html`은 설계·시연용 HTML 프로토타입, 루트 `index.html`·`workspace.*`는 개발 워크스페이스이므로 제품 화면과 구분한다. 흐름이 바뀌면 설계 보드(27개 화면)와 대조한다. 보드의 가입·로그인 화면 1~14번과 차주 일감 목록 16번은 현재 Flutter 설계를 따른다.
- 기존 브랜드 파랑 `#2563EB`, 밝은 회색, 큰 터치 영역, 쉬운 한국어를 유지한다. 색·글꼴은 `AppColors`·`AppTheme`에 모으고 화면 코드에 직접 쓰지 않는다. 주 색(버튼 등)은 `AppTheme`에서 `#2563EB`로 고정했으며 2026-11-03 웹 화면에서 버튼 색이 `#2563EB`인 것을 확인했다.
- 플랫폼에 따라 다른 기능(카메라·사진·위치·푸시·파일·권한·보안 저장소·외부 앱 연결)은 인터페이스 뒤에 두고 웹·앱 구현을 나눈다. `kIsWeb` 분기를 화면 곳곳에 흩뿌리지 않는다.
- Firebase Auth 연결은 `AuthRepository` 구현으로만 한다. 화면 코드가 Firebase SDK를 직접 부르지 않게 한다.
- 웹 베타는 GitHub Pages(`/FarmCargo/` 하위 경로)에 배포한다. 배포용 빌드는 `--base-href /FarmCargo/`를 쓰고, 주소는 해시 방식(`#/경로`)이라 새로고침과 직접 진입이 별도 서버 설정 없이 동작한다. 주소를 만들 때는 이 형식을 따른다(예: `.../FarmCargo/#/reset-password?token=...`).
- 배포된 웹의 소스·번들·샘플 데이터는 누구나 볼 수 있다. 비밀키·실제 개인정보·운영 계정 정보를 넣지 않는다. 서버가 없는 동안 가입·서류 입력 화면은 테스트 버전임을 화면에 알리고 실제 개인정보를 받지 않는다(`DemoNotice`). 서버가 연결되면 이 안내를 제거한다.
- 웹 베타에서 추가로 확인한다: 모바일 브라우저 크기·터치, 브라우저 뒤로 가기·새로고침·입력 보존, 한글 입력(조합 중 입력)과 폰트 표시, 첫 로딩 시간과 용량, 배포 후 이전 버전이 캐시로 남는지.
- 앱 단계에서 추가로 확인한다: Android·iOS 실기기, 권한 요청 문구와 거부 시 동작, 시스템 뒤로 가기, 키보드, 앱 ID·서명·개인정보 처리방침·스토어 심사 요건.
- 웹 확인 결과를 앱 동작 보장으로 보고하지 않는다. 실제 브라우저·기기를 확인하지 못했다면 코드 검사·컴파일만 했다고 명시한다.
- 웹용 `app/web/`의 제목·설명·테마색은 팜카고 기준으로 맞췄다(2026-11-03). 웹 아이콘(`app/web/icons/`, `favicon.png`)은 임시 트럭 아이콘이므로 정식 로고가 정해지면 교체한다. Android 앱 아이콘(`app/android/.../mipmap-*`)은 아직 Flutter 기본값이다.

## 1. 작업 전에 확인

- 사용하는 역할, 진입·이동 경로, 화면의 목적, 관련 요구사항 ID.
- 필요한 API·입력값·단위·권한과 현재 구현 여부.
- 기존 공통 컴포넌트·스타일·상태 관리·오류 표시 방식.
- 미정 정책이 화면 동작을 결정하는지 확인하고, 필요한 부분만 질문한다.

## 2. 화면과 코드의 책임

- 기존 구조 안에서 화면 표시·상태·업무 처리·통신의 책임을 구분한다. 화면마다 별도 방식의 API 호출·날짜·금액 포맷을 만들지 않는다.
- 공통 버튼·입력·목록·오류·로딩 요소를 재사용한다. 명확한 공통 요구가 없는 작은 기능에 과도한 추상화를 넣지 않는다.
- 업무 권한·배정·수수료 계산의 최종 판단은 서버와 일치시킨다. 클라이언트 검증은 사용자 안내이며 권한 보장을 대체하지 않는다.
- 실제 연결과 합성 데이터·시연 화면을 명확히 구분한다. 구현되지 않은 서버 응답을 실제 저장 성공으로 표시하지 않는다.

## 3. 팜카고 화면 기준

| 화면 | 현재 방향 | 임의로 정하지 않을 것 |
|---|---|---|
| 화주 홈 | 배차 작성·나의 배차 진입 | 다른 화주의 일감 노출 |
| 배차 작성 | 운송 조건 구조화 입력. 물량·품목·차종·상/하차 날짜(당착 또는 다음날 도착) 필수, 단가는 건당 또는 kg당, 부가세 별도 표시(요구사항 D01). 품목은 목록(소맥피·단백피·대두·대두박·팜박·옥수수)에서 고르고 없으면 직접 입력, 원산지는 국산·외국산 선택(D13) | 그 밖의 필수값, kg당 입력 단위·소수점, 원산지 필수 여부 |
| 나의 배차 | 본인 일감 조회·수정. 상차일 전날 15시(당일 배차는 당일 9시) 이후 취소 불가. 차주 선택·취소 알림. 차주 이름·차량번호·차종·톤수·별점 표시, 연락처는 표시하지 않음. 수락 후에도 상/하차지·품목 등은 수정 가능(차주에게 바로 알림), 시간은 수정 불가. 하차 증빙 사진 도착 시 예/아니오 확인(D04·D05·D06) | 조건 수정의 차주 거절 |
| 별점 평가 | 화주가 하차지 계근표·서명으로 운송 종료를 확인한 일감에만 차주에게 별 1~5개(별 1개 = 1점). 별점 혜택은 월간 별점 랭킹에 따른 차주 수수료율 감면(상위 5% 3%, 상위 10% 3.5%, D17) | 랭킹·감면 표시 화면 |
| 가입·로그인·복구 | 휴대폰 번호 로그인(이메일 없음), 필수 문자 인증, 약관, 역할별 서류(화주 사업자등록증은 사진만), 휴대폰 문자 인증 기반 비밀번호 재설정(요구사항 3절). 비밀번호 저장·검증은 프로토타입 Firebase Auth·출시 Argon2id이며 `AuthRepository` 뒤에서 연결 | 약관·권한 문구(참조 사진 없음), 심사·반려·보관, 가입 OCR 도입 시기 |
| 차주 인증 | 요구사항 3절 ‘차주 회원가입 흐름’(2026-11-04): 가입 조건 안내 → 이름·휴대폰 번호, 문자 인증·약관 → 비밀번호·확인 → 차량번호·차종·톤급 → 사업자등록증·통장 사본·운전면허증 사진 제출(미리보기 + 노란 ‘승인 대기’, 사업자등록증 항목 입력 없음) + 같은 화면 아래 전자세금계산서 전용 이메일·세금계산서 위수탁 동의서(2026-11-09) → 사측 대조·차량번호 지역 인증 → 완료 → 재로그인 | GPS 인증, 3영업일 심사, 심사 중 접근 범위, 반려 후 재제출 |
| 차주 홈 | 추천 맞춤 오더 | 추천 기준(별점·동선 반영 여부)을 임의 알고리즘으로 정하기 |
| 차주 ‘오더 찾기’ 탭 | 홈과 별도 탭(이름 ‘오더 찾기’, 2026-11-05), 게시글 형식 목록을 쭉 나열. 원하는 동선의 일거리 선택. 서버 접수 순 선착순 | 고정 6~7건 노출, 별점으로 순서·선택 기회 바꾸기(별점 혜택은 수수료 감면, D17), 필터·정렬 기준 |
| 일감 선택 결과 | 서버가 처리한 결과 반영. 선택이 성공하면 즉시 확정(화주 승인 없음). 시간이 겹치는 다건 선택은 막지 않음. 하루 최대 3건(상차일 기준) 초과는 서버 거절을 안내 | 서버 확인 전 배정 확정 표시 |
| 운송 증빙 | 상·하차 계근표, 하차 계근표 없으면 하차지 공장 사무실 직원 서명. 차주가 사진으로 올림. 하차 증빙만 즉시 화주에게 전달해 확인받고, 상차 계근표는 사진만(D05) | 가입 인증과 혼합 |
| 배차 질의(‘화주에게 전달’) | 차주가 배차 관련 질의를 쓰면 고객센터가 화주에게 전달하고 답을 앱으로 차주에게 보냄(D06) | 화주↔차주 직접 채팅·연락처 노출 |

## 4. 입력·상태·오류

- 각 입력에 의미·단위·필수 여부·오류 수정 방법을 제시한다. 사용자에게 필요한 설명을 화면에 쓴다.
- 화면마다 최초 로딩·새로고침·빈 목록·연결 실패·권한 부족·저장 중·저장 실패·성공 상태를 필요한 범위에서 구분한다.
- 저장·선택의 반복 입력을 적절히 제어하고, 실패·재시도 후 상태가 서버와 일치하도록 한다.
- 다른 차주가 먼저 선택한 일감은 서버 결과에 따라 목록·상세를 갱신하고 이해할 수 있는 안내를 한다.
- 삭제·취소와 같은 동작은 실제 적용 정책을 설명한다. 미정 취소 기한을 화면에 넣지 않는다.
- 화면 이동·오류·입력 중단 시 입력값 보존과 복원 필요성을 검토한다. 인증 자료·비밀정보를 임의로 장기 저장하지 않는다.
- 로그인 역할이 바뀌거나 로그아웃하면 이전 사용자의 일감·증빙·캐시가 노출되지 않게 한다.

## 5. 일관성과 사용성

- 공통 색·여백·글꼴·버튼·아이콘 기준을 따르고, 색만으로 상태를 구분하지 않는다.
- 긴 한글·큰 글씨·키보드·작은 화면에서 잘림과 가림을 확인한다. 조작 요소의 식별·접근성 이름·초점 처리를 고려한다.
- 사용자 화면에 DB 구조·내부 오류·비밀정보를 노출하지 않는다. 오류에는 사용자가 할 수 있는 다음 행동을 담는다.
- 카카오톡·전화 등 외부 앱 연결은 사용자가 선택한 명시 동작으로 구분한다. 메시지 자동 발송·자동 통화를 임의 추가하지 않는다.

## 6. 검증·완료 보고

변경한 화면의 실제 표시와 핵심 동선을 확인한다. 입력 검증·역할별 접근·선택 충돌·로딩·빈 상태·실패 재시도 중 변경과 관련된 동작을 우선 검증한다. 단순 문구 수정에는 적절한 화면 확인만으로 충분할 수 있다.

완료 시 변경 화면·사용 흐름·연결된 API·확인한 기기나 환경·미연결 부분을 보고한다. 실제 화면을 확인하지 못했다면 코드 검사만 수행했다고 명시한다.
