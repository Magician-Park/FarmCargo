# 백엔드·API·업무 처리 규칙

작성일: 2026-11-03
읽기 순서: [저장소 AGENTS.md](../../../AGENTS.md) → [현재 요구사항](../requirements.md) → 이 문서
DB를 변경하면 `database.md`, 화면 계약에 영향을 주면 `frontend.md`도 읽는다.

## 현재 개발 단계(Flutter 웹 베타 → 앱 출시)의 적용 범위

- 웹 베타를 거쳐 앱으로 출시하는 방침을 따른다. 실제 업무 API·DB 도입 여부는 저장소와 사용자 결정에서 확인한다.
- 로컬 정적 서버, 앱 안의 샘플 데이터(`Mock*Repository`)와 로컬 저장은 업무 백엔드·DB 연동과 다르다. 웹과 앱이 같은 서버 계약을 쓰도록 설계한다. 시연에서만 동작하는 권한 검사를 실제 보안으로 보고하지 않는다.
- DB·서버 구현이 필요한 작업은 실제 저장·권한·재시도·동시성을 설계하되, 이 문서가 기술 제품 선택이나 외부 서비스 연결을 미리 승인한 것은 아니다. 예외로 인증은 프로토타입 Firebase Auth·앱 출시 Argon2id로 정했다(3절). 다른 Firebase 서비스나 업무 DB는 이 결정에 포함되지 않는다.
- 웹 베타를 올리는 GitHub Pages는 정적 파일만 제공한다. 서버·DB가 필요한 베타 기능은 별도 호스팅을 정해야 하며, 그때 다른 도메인 호출을 위한 접근 허용(CORS)과 인증 설정을 설계한다.
- 클라이언트(웹·앱)는 같은 API를 쓴다. 웹 베타 사용자와 이후 앱 사용자가 같은 계정·데이터로 이어져야 하는지는 미정이므로 베타 데이터의 이전·초기화 방침을 정하기 전에 실제 데이터를 쌓지 않는다.

## 1. 작업 전 확인할 계약

- 관련 요구사항 ID와 실제 호출자·역할·대상 데이터.
- 요청·응답의 필드·형식·필수값·단위·시간대·오류·권한.
- 상태 변경과 DB 영향, 재시도·동시 요청 처리.
- 기존 API·서비스·저장소·인증·예외 처리 관례와 호환성.
- 사업 정책이 미정이면 계약의 그 부분을 임의로 채우지 않는다.

## 2. API 일관성

- 기존 프로젝트의 API 명명·응답·오류 형식을 따른다. 새 형식을 도입할 이유와 영향을 설명한다.
- 상태 변경은 명시적인 동작으로 처리하고 조회 요청의 부수 효과로 배정·취소·정산을 수행하지 않는다.
- 목록의 정렬·페이지 처리·필터 기준을 명시한다. 별점 혜택은 수수료 감면(D17)이며 별점 우선 정렬은 정하지 않았으므로 임의로 구현하지 않는다.
- 알 수 없는 필드·잘못된 값·허용되지 않은 상태 변경을 처리한다. 호출자가 임의 소유자·역할·심사 결과·수수료 값을 쓸 수 없게 한다.
- API 계약과 클라이언트 타입·예시를 함께 갱신한다. 문서 예시에는 합성 데이터만 사용한다.

## 3. 인증·권한

- 로그인 신원 확인과 해당 데이터에 대한 권한 검사를 구분한다. 로그인 아이디는 휴대폰 번호뿐이며, 가입 시 휴대폰 문자 인증을 거친 번호만 계정에 연결한다. 번호 표기(하이픈 등) 정규화 규칙을 서버에서 정한다. 비밀번호 재설정은 번호 인증 후 한 번만 쓸 수 있고 시간이 제한된 토큰으로 처리하며, 가입 여부를 응답으로 드러내지 않는다(문자 인증 방식은 확정, 토큰 유효 시간은 3분).
- 비밀번호 저장·검증은 프로토타입에서 Firebase Auth, 앱 출시 때 Argon2id로 한다(사용자 결정 2026-11-04). 비밀번호를 직접 저장하게 되면 평문이나 되돌릴 수 있는 암호화로 저장하지 않는다. 휴대폰 번호+비밀번호 로그인을 Firebase Auth로 구성하는 방법과 Argon2id로 옮기는 방법(기존 비밀번호 처리 포함)은 공식 문서로 확인한 뒤 설계한다.
- 화주의 목록·상세·수정·첨부 자료 접근에서 본인 소유 관계를 검사한다. 전달된 사용자 ID나 화면 제한만 신뢰하지 않는다.
- 인증된 차주만 접근하는 기능은 서버에서 인증 상태를 확인한다. 차주 서류(사업자등록증·통장 사본·운전면허증)와 차량번호 기반 지역 인증, 사측 대조 확인은 요구사항 3절의 흐름을 따르되 세부 대조 절차는 합의 후 구현하며 GPS 인증으로 확대하지 않는다.
- 관리자·고객센터 직원의 권한도 명시적으로 설계한다. 역할 이름만으로 모든 개인정보 접근을 허용하지 않는다.
- 다른 사용자 계정·일감·증빙의 존재나 내용이 권한 없는 응답·로그·파일 주소로 드러나지 않게 한다.

## 4. 배정·동시성·재시도

- 일감은 서버 접수 순으로 한 명만 원자적으로 선점하게 한다(D03 확정 방향). 접수 시각의 기준은 구체화한 뒤 구현한다. 별점 혜택은 수수료 감면(D17)이므로 별점으로 선점 순서나 이미 완료된 선점을 바꾸지 않는다.
- 동시 선택의 승패는 서버·DB에서 일관되게 결정한다. 화면에서 버튼을 숨기는 것으로 중복 배정을 막지 않는다.
- 성공한 배정·취소·정산이 재시도로 중복 실행되지 않게 설계한다. 필요한 경우 중복 요청 식별 키와 재사용 범위를 정한다.
- 상태 확인과 변경을 원자적으로 처리하고 충돌·실패 시 일관된 결과를 반환한다.
- 취소·수정·재공개의 실제 정책이 정해진 후 상태 전이를 구현한다. 가용 목록 제외와 원본 삭제를 구분한다.
- 장시간 작업·외부 연동 실패가 DB 상태에 미치는 영향을 검토한다. 필요 없는 큐·분산 시스템을 선제적으로 도입하지 않는다.

## 5. 수수료·제재·증빙·외부 연동

- 수수료는 **4%**이며 차주가 받는 운송비 안에서 떼고, 금액은 1원 미만 반올림한다. 부가세는 화주가 낸다(D09, 2026-11-05·09). 4%는 부가세를 포함한 운송비에 매긴다(2026-11-09). 운송비는 화주 → 팜카고 → 차주로 흐르며 차주 지급은 화주 정산일의 10일 뒤다(예: 5일 → 15일, 2026-11-09). 지급일은 은행 영업일 기준이며, 그날이 공휴일(주말 포함)이면 그 전 은행 영업일에 지급한다(2026-11-10). 이 영업일은 D14 제재의 영업일(월~토, 공휴일 포함)과 다르므로 같은 계산 함수를 쓰지 않는다. 수수료·감면 계산은 서버에서만 한다.
- 별점은 화주가 운송 종료(하차지 계근표·서명)를 확인한 일감에만 받는다. 별은 한 건에 1~5개다. 차주별 별 개수는 매월 1일 0시(서버 시각)에 초기화하고, 랭킹 계산과 수수료율 감면(상위 5% 3%, 상위 10% 3.5%)은 한 달 정산 때 서버가 적용하며, 최소 차주 수 없이 시작 때부터 적용한다. 별점이 같으면 공동 순위로 처리해 경계의 동점자도 모두 감면한다(D17·D18). 5%·10% 인원은 올림해 최소 1명은 감면한다(2026-11-09).
- 금액·세금·할인의 정밀도·반올림·계산 기준·변경 이력을 정의한다. 클라이언트 계산 값을 최종 정산 값으로 신뢰하지 않는다.
- 제재는 차주에게만 적용하며 단계(1회 1영업일·2회 7영업일·3회 30영업일 정지, 이후 누적 시 영구 정지, 영업일은 월~토·공휴일 포함, 최초 경고 1년 후 초기화)는 요구사항 D14를 따른다. 경고 부여와 블랙리스트 추가·해제는 관리자(대표이사) 승인으로 처리하고 자동 블랙리스트는 만들지 않는다. 취소한 날 기준 하루 3건째 취소는 과도한 취소로 기록한다. 승인은 대표이사와 지정된 공동 승인 담당자가 한다. 정지되면 잡아 둔 배차의 확정을 해제해 다시 공개하고 화주에게 알린다. 정지 기간 계산은 서버 시간(한국 시간)으로 하며, 1회 정지(1영업일)는 정지된 시각부터 24시간이고(일요일에 걸쳐도 24시간, 2026-11-11·12), 7·30영업일 정지는 정지 시각 기준으로 그 영업일 수 뒤 같은 시각에 끝난다(2026-11-12). 블랙리스트가 해제되면 경고 횟수를 0으로 되돌리되 이전 경고·블랙리스트 기록은 앱 서비스를 끝낼 때까지 보관하고(2026-11-12, 개인정보 법률 검토 필요), 대표이사·지정된 공동 승인 담당자·고객센터 담당자만 열람하게 한다(2026-11-12). 수락 후 조건 수정을 차주가 거절할 때, 화주가 수락 뒤 상/하차지를 바꾼 경우(변경 사유 메시지를 미리 보냈어도)와 차종을 잘못 입력한 경우는 패널티 없이 처리하고, 그 밖의 거절은 D14 경고 1회로 기록해 오더 수락을 막는다(D04, 2026-11-11). 블랙리스트에 오른 휴대폰 번호의 가입 요청은 대표이사 승인으로 해제되기 전까지 서버에서 거절한다. 반려된 가입 신청의 기록과 서류 사진은 반려 즉시 삭제한다(D15). 화주에게는 패널티를 두지 않는다.
- 운송 증빙과 가입 인증의 목적·보관·열람 권한을 분리한다. 하차 증빙 확인은 화주 예/아니오 응답, 30분마다 재알림, 1시간 10분 무응답 시 고객센터 알림을 서버 작업으로 처리한다(D05). 증빙 사진은 운송이 끝난 날부터 3개월, 고객센터 녹음·기록은 3개월 뒤 DB에서 삭제한다. 가입 서류는 대표이사와 심사 담당자만 열람하고 탈퇴 3개월 후 폐기한다(D07·D15). 파일 형식·크기·접근 제어·처리 실패를 설계한다.
- 배차·취소·증빙 알림은 앱 푸시와 카카오 알림톡으로 보낸다(D02, 2026-11-11). 발송 업체·템플릿·비용이 정해지기 전에는 실제 발송을 연결하지 않고, 테스트와 운영 발송을 나눈다. 고객센터 카카오톡 상담 대화를 자동 수집하는 연동은 만들지 않는다. 연락 상대는 해당 화주·차주이며 화주↔차주 연락처는 API 응답에 넣지 않는다(D06). 일감 선택은 서버가 즉시 확정하고 화주에게 알리며, 상차일 전날 15시(당일 배차 오더는 당일 9시) 이후 취소 요청과 상차일 기준 하루 3건을 넘는 수락 요청은 서버에서 거절한다(D02·D03·D04). 시각 판단은 서버 시간(한국 시간)으로 한다.
- 가입 서류 OCR은 쓰지 않는다(D08). 인증 완료는 사측 대조 확인으로만 처리한다.
- 멤버십은 추후 도입 예정이라 이번 설계에서 제외한다(D18, 2026-11-05). 멤버십 혜택·요금 API를 만들지 않는다.
- 실제 메시지·결제·세금계산서 발행 등 외부 효과가 있는 연동은 테스트 모드와 운영 환경을 분리하고 대상·영향을 명시한다.
- 앱이 차주 대신 세금계산서를 발행하는 방식(D09)은 차주에게 회원가입 서류 제출 단계에서 별도 위수탁 동의서를 받는다(2026-11-09). 동의 기록이 없는 차주 몫은 대신 발행하지 않고, 세무 검토 전에는 실제 발행 연동을 만들지 않는다.

## 6. 오류·로그·설정

- 사용자가 이해할 오류 응답과 내부 진단 정보를 구분한다. 내부 경로·SQL·비밀정보를 응답으로 노출하지 않는다.
- 요청을 추적할 식별자와 필요한 업무 결과를 기록하되 비밀번호·토큰·실제 서류·서명·전체 개인정보를 로그에 남기지 않는다.
- 비밀정보는 환경에 맞는 비밀 관리 방식을 사용한다. Firebase 서비스 계정 키 같은 관리자 비밀키는 저장소·웹 번들에 넣지 않는다. 예시 설정 파일에는 값의 이름과 용도만 기록한다.
- 개발·테스트·운영 환경의 연결과 권한을 구분한다. 실제 데이터·외부 서비스를 테스트 대상으로 오인하지 않는다.

## 7. 검증·완료 보고

변경에 맞게 화주 소유권 차단, 차주 인증 조건, 정상·오류 API 계약, 동시 일감 선택, 중복 요청, 상태 전이, DB 실패 처리를 검증한다. 실제 외부 발행·결제를 검증 목적으로 임의 수행하지 않는다.

완료 시 변경 API·업무 규칙·DB 영향·검증 결과·미정 정책·실제 연결 여부를 보고한다. 구현하지 않은 외부 서비스가 작동한다고 표현하지 않는다.
