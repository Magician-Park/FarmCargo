# DB 설계·변경 규칙

작성일: 2026-11-03
읽기 순서: [저장소 AGENTS.md](../../../AGENTS.md) → [현재 요구사항](../requirements.md) → 이 문서
DB 제품·ORM·마이그레이션 도구는 실제 프로젝트 확인 후 정한다.

## 현재 개발 단계(Flutter 웹 베타 → 앱 출시)의 적용 범위

- 웹 베타를 거쳐 앱으로 출시하는 방침을 따른다. 실제 업무 API·DB 도입 여부는 저장소와 사용자 결정에서 확인한다.
- 로컬 정적 서버, 앱 안의 샘플 데이터(`Mock*Repository`)와 로컬 저장은 업무 백엔드·DB 연동과 다르다. 웹과 앱이 같은 서버 계약을 쓰도록 설계한다. 시연에서만 동작하는 권한 검사를 실제 보안으로 보고하지 않는다.
- DB·서버 구현이 필요한 작업은 실제 저장·권한·재시도·동시성을 설계하되, 이 문서가 기술 제품 선택이나 외부 서비스 연결을 미리 승인한 것은 아니다. 예외로 인증은 프로토타입 Firebase Auth·앱 출시 Argon2id로 정했다(`backend.md` 3절). 업무 DB 제품은 이 결정에 포함되지 않는다.
- 클라이언트(웹·앱)는 같은 API를 쓴다. 웹 베타 사용자와 이후 앱 사용자가 같은 계정·데이터로 이어져야 하는지는 미정이므로 베타 데이터의 이전·초기화 방침을 정하기 전에 실제 데이터를 쌓지 않는다.

## 1. 설계 전에 제시할 내용

- 기능과 관련 요구사항 ID, 저장할 정보와 소유자.
- 기존 테이블과의 관계, 새 필드의 목적·형식·필수 여부·기본값.
- 유일성·참조 무결성·조회 범위·필요한 인덱스와 그 이유.
- 데이터 생성·조회·수정·보관·삭제 주체와 상태 변경 조건.
- 기존 데이터 영향, 마이그레이션, 검증·복구 방법.

기술적으로 정할 수 있는 것은 기존 관례와 이유를 설명하고 진행한다. 사업 정책이 미정인 필드·기본값·상태 전이는 사용자에게 확인한다.

## 2. 데이터 구조 후보와 경계

아래는 논리적 설계 후보다. 테이블 수·이름·관계가 확정된 스키마가 아니다.

| 정보 묶음 | 담을 역할 | 주의할 경계 |
|---|---|---|
| 계정·역할·사업자 | 사용자 식별(휴대폰 번호가 유일한 아이디), 화주·차주 권한. 비밀번호는 프로토타입에서 Firebase Auth가 관리하고, 앱 출시 때는 Argon2id 해시만 저장 | 한 계정의 복수 역할 허용 여부, 번호 변경·재사용 규칙, Firebase Auth 사용자와 업무 DB 계정의 연결, Argon2id로 옮기는 방법 미정 |
| 차량·인증 | 차량 정보(차량번호·차종·톤급), 사업자·지역 인증 상태, 업로드 서류(사업자등록증·통장 사본·운전면허증) 사진과 사측 대조 결과·반려 사유 | GPS 인증이 아님. 심사·보완·반려·보관 정책 미정 |
| 일감 | 소유 화주, 운송 조건, 게시 정보 | 다른 화주의 조회 차단 |
| 선택·배정 이력 | 차주의 선택 요청(서버 접수 시각)과 배정 결과 | 서버 접수 순 단일 선점, 선택 즉시 확정(D02). 취소 시 이력은 남기고 일감은 다시 공개(D04). 하루 수락 최대 3건(상차일 기준)은 동시 요청에서도 서버가 보장. 별점 혜택 방식 미정 |
| 운송 증빙 | 계근표·하차 서명 사진과 해당 운송의 연결, 화주 확인(예/아니오·무응답) 기록, 고객센터 알림 기록 | 가입 인증과 구분, 파일 열람 제한. 사진 3개월 뒤 소멸(앱/DB 범위 확인 필요) |
| 고객센터 처리 | 전달 내용·확인 결과·담당 이력 | 통화 상대·응대 시간·기록 상세 미정 |
| 리뷰·제재·혜택 | 별점·경고(사유·부여자·일시)·정지 기간·블랙리스트(승인자)·혜택·멤버십 이력 | 경고는 차주만. 경고 1년 초기화 기준일은 최초 경고일. 할인 공식·멤버십 가격을 임의로 정하지 않음 |
| 정산 | 수수료·조정·정산 내역 | 요율·부담자·계산·차감 방식 미정 |

## 3. 형식·단위·상태

- 기존 이름 규칙을 따른다. 단위가 다른 값을 같은 필드에 혼용하지 않는다.
- 금액·단가·세금·수수료의 통화·단위·정밀도·반올림 규칙을 명시한다. 확정 전 계산식을 넣지 않는다.
- 물량의 단위·정밀도를 정하고 품목명과 분리한다. 근거 없는 품목 사전·톤수 기본값을 만들지 않는다.
- 날짜만 필요한 값과 실제 시각을 구분한다. 운송 현지 시간·저장 시간대·표시 변환 기준을 정한다. 서버의 로컬 시간에 조용히 의존하지 않는다.
- 상태값은 의미·전이 조건·변경 주체를 문서화한다. 게시·선택·배정·운행·취소·정산 상태를 구분할지 검토한다.
- 필수값·참조 관계·중복 금지 등 DB가 보장할 제약과 애플리케이션 검증을 함께 설계한다.

## 4. 권한·동시성·보존

- 일감에는 조회 권한을 판정할 소유 관계가 있어야 한다. 화면에서 숨기는 것만으로 화주 간 비공개를 구현하지 않는다.
- 조회 목록뿐 아니라 상세·수정·첨부 파일 접근에서도 같은 권한을 확인한다.
- 같은 일감은 서버 접수 순으로 한 명만 선점하며, 완료된 선점은 별점 혜택으로 바꾸지 않는다(D03). 양립할 수 없는 배정이 동시에 성립하지 않도록 트랜잭션·제약 등 선택한 DB의 방법으로 보장한다. 클라이언트의 조회 후 쓰기만으로 처리하지 않는다.
- 재시도·중복 요청이 배정·정산·혜택을 중복 생성하지 않게 설계한다.
- 가용 목록 제외와 데이터 삭제를 구분한다. 배정·취소·변경 이력의 보존 방식을 설계한다.
- 증빙 원본의 저장 위치·접근 권한·보관 기간을 정한다. 운송 증빙 사진은 3개월, 가입 서류 사진은 탈퇴 후 3개월이 지나면 폐기한다(D05·D15). 영구 보관을 임의로 선택하지 않는다.

## 5. 마이그레이션·복구

- 스키마 변경은 저장소에서 재현 가능한 마이그레이션으로 남긴다. 이미 적용된 공유 마이그레이션을 조용히 고치지 않는다.
- 기존 데이터를 새 필수 필드·제약에 맞추는 순서와 실패 시 처리를 고려한다.
- 개발·테스트·운영 연결을 확인한다. 테스트가 실제 사용자 데이터에 쓰지 않게 한다.
- 실제 데이터 삭제·초기화·되돌리기 어려운 변경은 대상·영향·백업·복구안을 제시하고 필요한 승인을 받는다.
- 되돌림 스크립트가 안전하지 않은 변경은 그 한계와 복원 방법을 명시한다.

## 6. 검증·보고

변경 범위에 맞게 마이그레이션 적용, 기존 데이터 호환성, 제약, 권한, 동시 선택·중복 요청을 검증한다. 소량의 합성 테스트 데이터를 사용하고 실제 개인정보를 복사하지 않는다.

완료 보고에는 변경 스키마·마이그레이션 파일·검증 결과·데이터 영향·복구 한계를 포함한다. 설계만 한 것과 실제 DB에 적용한 것을 구분한다.
