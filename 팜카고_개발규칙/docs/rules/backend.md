## 현재 개발 단계(Flutter 웹 베타 → 앱 출시)의 적용 범위

- 웹 베타를 거쳐 앱으로 출시하는 방침을 따른다. 실제 업무 API·DB 도입 여부는 저장소와 사용자 결정에서 확인한다.
- 로컬 정적 서버, 앱 안의 샘플 데이터(`Mock*Repository`)와 로컬 저장은 업무 백엔드·DB 연동과 다르다. 웹과 앱이 같은 서버 계약을 쓰도록 설계한다. 시연에서만 동작하는 권한 검사를 실제 보안으로 보고하지 않는다.
- DB·서버 구현이 필요한 작업은 실제 저장·권한·재시도·동시성을 설계하되, 이 문서가 기술 제품 선택이나 외부 서비스 연결을 미리 승인한 것은 아니다.
- 웹 베타를 올리는 GitHub Pages는 정적 파일만 제공한다. 서버·DB가 필요한 베타 기능은 별도 호스팅을 정해야 하며, 그때 다른 도메인 호출을 위한 접근 허용(CORS)과 인증 설정을 설계한다.
- 클라이언트(웹·앱)는 같은 API를 쓴다. 웹 베타 사용자와 이후 앱 사용자가 같은 계정·데이터로 이어져야 하는지는 미정이므로 베타 데이터의 이전·초기화 방침을 정하기 전에 실제 데이터를 쌓지 않는다.

## 1. 작업 전 확인할 계약

- 관련 요구사항 ID와 실제 호출자·역할·대상 데이터.
- 요청·응답의 필드·형식·필수값·단위·시간대·오류·권한.
- 상태 변경과 DB 영향, 재시도·동시 요청 처리.
- 기존 API·서비스·저장소·인증·예외 처리 관례와 호환성.
- 사업 정책이 미정이면 계약의 그 부분을 임의로 채우지 않는다.

## 2. API 일관성

- 기존 프로젝트의 API 명명·응답·오류 형식을 따른다. 새 형식을 도입할 이유와 영향을 설명한다.
- 상태 변경은 명시적인 동작으로 처리하고 조회 요청의 부수 효과로 배정·취소·정산을 수행하지 않는다.
- 목록의 정렬·페이지 처리·필터 기준을 명시한다. 별점 우선순위 정책을 임의 정렬로 구현하지 않는다.
- 알 수 없는 필드·잘못된 값·허용되지 않은 상태 변경을 처리한다. 호출자가 임의 소유자·역할·심사 결과·수수료 값을 쓸 수 없게 한다.
- API 계약과 클라이언트 타입·예시를 함께 갱신한다. 문서 예시에는 합성 데이터만 사용한다.

## 3. 인증·권한

- 로그인 신원 확인과 해당 데이터에 대한 권한 검사를 구분한다.
- 화주의 목록·상세·수정·첨부 자료 접근에서 본인 소유 관계를 검사한다. 전달된 사용자 ID나 화면 제한만 신뢰하지 않는다.
- 인증된 차주만 접근하는 기능은 서버에서 인증 상태를 확인한다. 사업자·지역 인증의 실제 확인 방법은 합의 후 구현한다.
- 관리자·고객센터 직원의 권한도 명시적으로 설계한다. 역할 이름만으로 모든 개인정보 접근을 허용하지 않는다.
- 다른 사용자 계정·일감·증빙의 존재나 내용이 권한 없는 응답·로그·파일 주소로 드러나지 않게 한다.

## 4. 배정·동시성·재시도

- 먼저 선택 우선 방향을 구현할 때 판정 시점·추가 승인·별점 혜택과의 관계를 먼저 구체화한다.
- 동시 선택의 승패는 서버·DB에서 일관되게 결정한다. 화면에서 버튼을 숨기는 것으로 중복 배정을 막지 않는다.
- 성공한 배정·취소·정산이 재시도로 중복 실행되지 않게 설계한다. 필요한 경우 중복 요청 식별 키와 재사용 범위를 정한다.
- 상태 확인과 변경을 원자적으로 처리하고 충돌·실패 시 일관된 결과를 반환한다.
- 취소·수정·재공개의 실제 정책이 정해진 후 상태 전이를 구현한다. 가용 목록 제외와 원본 삭제를 구분한다.
- 장시간 작업·외부 연동 실패가 DB 상태에 미치는 영향을 검토한다. 필요 없는 큐·분산 시스템을 선제적으로 도입하지 않는다.

## 5. 수수료·제재·증빙·외부 연동

- 수수료 방식은 앱 제작자가 결정할 항목이다. 일감별·총매출 기준이나 2%를 조용히 기본값으로 채택하지 않는다.
- 금액·세금·할인의 정밀도·반올림·계산 기준·변경 이력을 정의한다. 클라이언트 계산 값을 최종 정산 값으로 신뢰하지 않는다.
- 경고 2회 제한 방향과 제한 일수·자동 적용 여부·블랙리스트 조건을 구분한다. 영구 정지·자동 해제를 임의 구현하지 않는다.
- 운송 증빙과 가입 인증의 목적·보관·열람 권한을 분리한다. 파일 형식·크기·접근 제어·처리 실패를 설계한다.
- 고객센터 카카오톡·전화 확인 설명을 외부 API 자동 연동의 승인으로 해석하지 않는다.
- 실제 메시지·결제·세금계산서 발행 등 외부 효과가 있는 연동은 테스트 모드와 운영 환경을 분리하고 대상·영향을 명시한다.

## 6. 오류·로그·설정

- 사용자가 이해할 오류 응답과 내부 진단 정보를 구분한다. 내부 경로·SQL·비밀정보를 응답으로 노출하지 않는다.
- 요청을 추적할 식별자와 필요한 업무 결과를 기록하되 비밀번호·토큰·실제 서류·서명·전체 개인정보를 로그에 남기지 않는다.
- 비밀정보는 환경에 맞는 비밀 관리 방식을 사용한다. 예시 설정 파일에는 값의 이름과 용도만 기록한다.
- 개발·테스트·운영 환경의 연결과 권한을 구분한다. 실제 데이터·외부 서비스를 테스트 대상으로 오인하지 않는다.

## 7. 검증·완료 보고

변경에 맞게 화주 소유권 차단, 차주 인증 조건, 정상·오류 API 계약, 동시 일감 선택, 중복 요청, 상태 전이, DB 실패 처리를 검증한다. 실제 외부 발행·결제를 검증 목적으로 임의 수행하지 않는다.

완료 시 변경 API·업무 규칙·DB 영향·검증 결과·미정 정책·실제 연결 여부를 보고한다. 구현하지 않은 외부 서비스가 작동한다고 표현하지 않는다.
